# MVP 开发计划与实现顺序

> 对应《中枢 Nexus · 个人工作台系统设计文档》第 9 章 **V0 · 打通闭环**。
> 目标：用最小代价验证"这个个人工作台到底有没有用"，每阶段都可独立交付、独立验证、独立提交。

---

## 一、MVP 范围（V0 打通闭环）

设计文档定义的 V0 交付物：

> 工作台骨架 + 3 内置组件 + 飞书 webhook + 最简每日总结 Agent

拆解后，MVP 由四个 Phase 组成，逐步把"界面可 DIY → 数据可沉淀 → 信息可流入 → AI 可办事"这条闭环打通。

---

## 二、实现顺序的总原则

1. **先确定性，后不确定性**（对应"先 workflow 后 agent"）：先把"数据能存、能读、能改"这类确定能力做扎实，再引入"让 AI 现场决策"的不确定能力。
2. **先不依赖外部凭证，后依赖外部凭证**：飞书 webhook 需要应用配置、每日总结 Agent 需要 LLM key，都是外部依赖；工作台组件与持久化则完全本地可控，先做。
3. **每阶段可独立交付、独立验证、独立提交**：做完一个 Phase 跑通冒烟测试即提交，避免把风险积压到最后。

---

## 三、阶段划分总览

| Phase | 名称 | 目标 | 关键交付物 | 状态 |
|---|---|---|---|---|
| Phase 1 | 工作台组件 DIY | "界面可 DIY" | Spring Boot 骨架 + Vue3 + Widget SDK + 拖拽布局 + 待办持久化 | ✅ 已完成 |
| Phase 2 | 组件配置化与持久化 | "数据可沉淀" | 便签/快捷链接后端持久化 + 组件配置面板 + Widget config schema | ✅ 已完成 |
| Phase 3 | 消息接入 | "信息可流入" | 通用 webhook 接收端点 + 消息流组件 + 消息统一模型 | ✅ 已完成 |
| Phase 4 | 每日总结 Agent | "AI 可办事" | LangGraph 编排服务 + 每日消化任务 + 总结落库 | ✅ 已完成 |
| Phase 5 | 组件配置增强 + 订阅推送 | "信息自动流入" | 组件 configSchema 完整化 + RSS/B站订阅抓取 + 去重入流 | ✅ 已完成 |

---

## 四、各阶段详述

### Phase 1 ✅ 工作台组件 DIY（已完成）

**目标**：把"工作台 + 组件化 + 拖拽布局"这个最核心的形态跑出来。

**交付物**：
- 后端：Spring Boot 2.7 骨架，controller/service/repository 分层，统一响应、全局异常处理、Flyway、H2、Actuator
- 前端：Vue 3 + TS + Vite，Widget SDK（注册表 + 渲染器），4 个内置组件（时钟/待办/便签/快捷链接），grid-layout-plus 拖拽 + 防抖自动保存
- 部署：docker-compose + 前后端 Dockerfile

**验收标准**：拖拽、缩放组件，刷新后布局仍在（后端持久化）；待办可增删改查。

### Phase 2 ✅ 组件配置化与持久化（已完成）

**目标**：让"组件"不仅摆得上、动得了，还能"存得下、配得了"——数据不丢、可配置，Widget SDK 具备"可配置组件"能力。

**交付物**：
- 后端新增 `note`（便签）、`link`（快捷链接）两张表及 CRUD API
- 前端便签组件、快捷链接组件从 localStorage 改为后端持久化
- Widget SDK 支持组件声明 `configSchema`（可配置项）
- 通用组件配置面板：点击组件 → 弹出设置，编辑组件专属配置

**验收标准**：便签、快捷链接刷新后不丢、跨设备一致；点组件能打开配置面板并保存生效。

### Phase 3 ✅ 消息接入（已完成）

**目标**：让外部信息能"流入"工作台，形成统一消息模型。

**交付物**：
- 后端 `message` 表 + 统一消息模型（来源/渠道/发送者/内容/时间）
- 通用 webhook 接收端点 `POST /api/messages`（任何来源 POST JSON 即可入流）
- 前端"消息流"组件（第 5 个内置组件）
- 邮件 / RSS 接入（可选，作为消息来源的 Adapter 示例）

**验收标准**：curl 模拟第三方 POST 消息，工作台消息流组件实时/刷新可见。

### Phase 4 ✅ 每日总结 Agent（已完成）

**目标**：让 AI 基于沉淀的数据"办事"，打通记忆闭环。

**交付物**：
- Python LangGraph 编排服务（`agent/`，固定 workflow 子图：fetch→aggregate→summarize→save）
- 可插拔 LLM 客户端：OpenAI 兼容接口 + 无 key 时规则式降级
- Spring Task 定时触发"消化"任务，把当天消息/待办/便签喂给 LLM 生成总结
- `daily_summary` 表落库 + 前端每日总结组件展示

**验收标准**：手动或定时触发，产出当天工作总结并落库展示。✅ 已达成

### Phase 5 ✅ 组件配置增强 + 订阅推送（已完成，V1 起始）

**目标**：让组件"配得了"（配置面板完整化），让信息"自动流入"（订阅 RSS/B站）。

**交付物**：
- 组件配置增强：5 个内置组件声明 configSchema 并消费 config
- 订阅源 CRUD + 可插拔抓取器（RSS 用 Rome、B 站用 wbi 签名）+ 定时抓取 + 去重 + 入消息流
- 订阅管理组件（第 7 个内置组件）

**验收标准**：添加 RSS/B站订阅，手动或定时抓取，新内容自动进入消息流。✅ 已达成

## 五、为什么这样排序

| 理由 | 说明 |
|---|---|
| 先形态后能力 | 没有工作台骨架，消息和总结无处安放；Phase 1 是一切的地基 |
| 先沉淀后流入 | 先解决"数据存哪"（Phase 2），再解决"数据从哪来"（Phase 3），最后"数据怎么用"（Phase 4） |
| 依赖解耦 | Phase 2 纯本地、零外部凭证，随时能开发；Phase 3/4 依赖飞书配置与 LLM key，需提前准备 |
| 每步可验证 | 每个 Phase 都有清晰的验收标准，做完即可冒烟测试并提交 |
